# ariadne

Go-микросервис для очистки GPS-маршрутов (устранение «коллизий»/глюков). Работает **асинхронно**: клиент сдаёт маршрут → получает `taskKey` → сервис чистит его в фоне → по готовности дёргает callback и/или клиент забирает результат по `taskKey`.

Хранилище задач и результатов — **Redis** (логическая БД 10, TTL 1 час). Обработку ведёт пул воркеров (число из env). Два транспорта: **REST** и **gRPC**.

## Асинхронный поток

```
1. Клиент → POST /v1/tasks {routeCompressed}          → 202 {taskKey}
2. Сервис: карточка задачи (pending) в Redis + в очередь
3. Воркер: берёт из очереди → чистит → пишет результат (done) или ошибку (failed) в Redis
4. Воркер → POST на CALLBACK_URL с taskKey            (готово; если CALLBACK_URL задан)
5. Клиент → GET /v1/tasks/{taskKey}                    → статус + очищенный маршрут + длина
             GET /v1/tasks/{taskKey}/debug             → разбор по стадиям
```

Все ключи задачи живут в Redis 1 час (`RESULT_TTL`), потом авто-удаление.

### Очередь: задача не пропадает

Очередь — **поток Redis** (stream) с группой потребителей, а не список. Разница в том, что происходит между выдачей и сохранением результата.

Со списком номерок снимался насовсем: умер воркер или моргнул Redis в этом промежутке — задача переставала существовать где-либо, кроме памяти процесса. Карточка висела в `pending` до конца TTL, клиент опрашивал её час и не дожидался ничего.

Теперь задача **числится за тем, кто её взял**, пока он не распишется:

```
взял (XREADGROUP) → посчитал → СОХРАНИЛ результат → расписался (XACK)
                                      ↑
                        не сохранилось — расписки нет,
                        задачу вернут в работу
```

**Уборщик** (горутина в пуле, раз в минуту) забирает задачи, выданные и не подтверждённые дольше порога, и кладёт обратно в очередь. Порог — не отдельная настройка, а `2 × (RESOLVE_TIMEOUT + таймауты Redis)`: живой воркер дольше задачу держать не может, его самого обрывает таймаут. Отдельной ручкой её однажды поставили бы меньше времени обработки, и уборщик начал бы отбирать задачи у живых воркеров. Вычисленный порог печатается в лог на старте.

**Предел попыток — 5.** Номер попытки едет внутри записи (счётчик выдач самого Redis не годится: возврат в очередь кладёт новую запись, и счёт начался бы с нуля). Задача, которая пять раз обрывала обработку, помечается `failed` с внятной причиной, а не гоняется по кругу вечно — иначе ядовитый вход выглядел бы как «сервис сам перезапускается».

## REST API

### POST /v1/tasks — сдать задачу

Мгновенно принимает маршрут в очередь. **Вход не декодится** (это работа воркера) — submit быстрый.

**Запрос:**
```json
{ "routeCompressed": "<base64(zlib(JSON))>" }
```

**Ответ 202:**
```json
{ "taskKey": "a1b2c3d4-..." }
```

`taskKey` — UUID, уникальность гарантируется записью в Redis через `SET NX`.

### GET /v1/tasks/{taskKey} — статус и результат

**Ответ 200:**
```json
{
  "taskKey": "a1b2c3d4-...",
  "status": "done",
  "routeCompressed": "<base64(zlib(JSON))>",
  "lengthMeters": 1168113.85,
  "degraded": true,
  "warnings": ["fill_gaps: budget spent, 35 of 294 gaps left straight — mileage understated"]
}
```

- `status` — `pending` (в очереди/считается) / `done` (готово) / `failed` (упало)
- `routeCompressed` — только при `status: done` (очищенный маршрут в том же сжатом формате)
- `lengthMeters` — длина очищенного маршрута в метрах; **присутствует всегда** (в `pending`/`failed` равна `0`), осмысленна при `done`. Поля без `omitempty`, чтобы клиент отличал длину `0` от отсутствия поля
- `error` — только при `status: failed` (текст, почему упало: битый вход, слишком много точек, < 2 точек после чистки и т.п.)
- `degraded` — **«километражу верить с оговоркой»**. Задача выполнена, маршрут настоящий, но неполный: конвейеру не хватило времени или не был задан маршрутизатор, и часть дыр осталась прямыми через поля. Поля нет, когда всё в порядке
- `warnings` — та же оговорка словами, для человека при разборе. Поля нет, когда предупреждений не было
- `404 NOT_FOUND` — задачи с таким `taskKey` нет (не создавали или протухла по TTL)

> **Почему `degraded` полем, а не значением `status`.** Новое значение статуса сломало бы живого клиента: он сверяется с `done`, не совпало бы — и готовый результат ушёл бы в мусор, а задача считалась бы вечно незавершённой. Поле старый клиент просто не заметит. Но заметить его надо: иначе заниженный километраж и дальше будет считаться точным.

> ⚠️ **Дорисованные точки в ответе пока не помечены.** В результате есть точки, которых не было во входе (их проложила дорисовка по дорожной сети, время на них разложено по доле пути) — отличить их от наблюдений сейчас нельзя. Конвейер их помечает (`RunState.Synthetic`), но до карточки задачи пометки не доходят. Решение 2026-07-27 (вариант Б) требует отдавать их отдельным полем; поле в публичный контракт ещё не добавлено.

### GET /v1/tasks/{taskKey}/debug — разбор по стадиям

**Ответ 200:**
```json
{
  "taskKey": "a1b2c3d4-...",
  "status": "done",
  "debug": [
    { "name": "sort_by_time", "pointsBefore": 3016, "pointsAfter": 3016, "elapsed": "1.2ms" },
    {
      "name": "core",
      "pointsBefore": 3016, "pointsAfter": 1946, "elapsed": "2.1s",
      "extra": {
        "roadPasses": 4, "roadBanned": 129, "roadAsked": 1730,
        "stopsTotal": 7, "stopsTrusted": 1, "stopsFrozen": 1,
        "split": 0, "spread": 1155, "amnesty": 106, "loops": 0,
        "snapMedianM": 5.2, "snapFraction": 1, "degraded": false,
        "kmBefore": 3000.4, "kmAfter": 288.1
      }
    },
    {
      "name": "fill_gaps",
      "pointsBefore": 667, "pointsAfter": 1114, "elapsed": "0.9s",
      "extra": {
        "gaps": 29, "filled": 27, "addedM": 32104.5, "addedPts": 447,
        "reasons": { "принято": 27, "крюк": 1, "физика": 1 },
        "degraded": false
      }
    }
  ]
}
```

`debug` заполнен при `status: done`. Поле `extra` есть у стадий, которым есть что рассказать: по «точек было / стало» ничего не понять — чистка может выбросить половину трека и быть правой. У упавшей стадии заполняется `error`, и статистика по уже пройденным при этом НЕ теряется. `404` — задачи нет.

### Прочее

- `GET /healthz` — liveness, `200 ok`.
- `GET /readyz` — readiness, `503` при shutdown.
- `GET /swagger/*` — Swagger UI (если `SWAGGER_ENABLED=true`).

### Ошибки REST

| Код | HTTP | Когда |
|---|---|---|
| `INVALID_REQUEST` | 400 | Невалидный JSON, пустой `routeCompressed`, тело > `MAX_BODY_BYTES` |
| `NOT_FOUND` | 404 | Нет задачи с таким `taskKey` |
| `INTERNAL` | 500 | Внутренняя ошибка (например, Redis недоступен) |

Формат ошибки:
```json
{ "error": { "code": "INVALID_REQUEST", "message": "routeCompressed is required" } }
```

`requestId` — в заголовке `X-Request-ID` (не в теле). Ошибки самой обработки маршрута (битый вход, слишком много/мало точек) НЕ приходят как HTTP-ошибка submit'а — они всплывают в `status: failed` + `error` при опросе.

## gRPC API — `ariadne.v1.RouteService`

```proto
service RouteService {
  rpc SubmitTask   (SubmitTaskRequest)    returns (SubmitTaskResponse);
  rpc GetTask      (GetTaskRequest)        returns (GetTaskResponse);
  rpc GetTaskDebug (GetTaskDebugRequest)   returns (GetTaskDebugResponse);
}

message SubmitTaskRequest  { string route_compressed = 1; }
message SubmitTaskResponse { string task_key = 1; }

message GetTaskRequest  { string task_key = 1; }
message GetTaskResponse {
  string task_key = 1;
  string status = 2;             // pending / done / failed
  string route_compressed = 3;   // при done
  double length_meters = 4;      // при done
  string error = 5;              // при failed
  bool degraded = 6;             // при done: километражу верить с оговоркой
  repeated string warnings = 7;  // при done: та же оговорка словами
}

message GetTaskDebugRequest  { string task_key = 1; }
message GetTaskDebugResponse {
  string task_key = 1;
  string status = 2;
  repeated StageStats debug = 3;
}
```

**Коды ошибок gRPC:**

| Код | Когда |
|---|---|
| `INVALID_ARGUMENT` | Пустой `route_compressed` или пустой `task_key` |
| `NOT_FOUND` | Нет задачи с таким `task_key` |
| `RESOURCE_EXHAUSTED` | Сообщение > `GRPC_MAX_RECV_MSG_SIZE` |
| `INTERNAL` | Внутренняя ошибка (Redis и т.п.) |

`x-request-id` возвращается в response-метаданных (и при успехе, и при ошибке). Есть стандартный `grpc.health.v1.Health/Check`; server reflection — по `GRPC_REFLECTION`.

## Callback (Go → Laravel)

Когда воркер закончил задачу (`done` ИЛИ `failed`), он дёргает внешнюю систему:

- **Метод:** POST на `CALLBACK_URL` с подстановкой плейсхолдера `{taskKey}` (напр. `https://laravel/api/ariadne/{taskKey}`).
- **Тело:** `{ "taskKey": "...", "status": "done|failed" }` (основной сигнал — `taskKey` в URL; по нему клиент идёт в `GET /v1/tasks/{taskKey}`).
- **Ретраи:** на сетевую ошибку и 5xx — до `CALLBACK_RETRIES` раз с бэкоффом; на 4xx не повторяет.
- **Выключение:** пустой `CALLBACK_URL` → коллбэки не шлются.

> Тело/метод — разумные дефолты; при уточнении контракта от команды меняются в `internal/callback`.

## Формат routeCompressed

Совместим с PHP-backend:
```
Кодирование:  json_encode(points) → gzcompress(level=9) → base64_encode
Декодирование: base64_decode → gzuncompress → json_decode
```
PHP `gzcompress()` — это **zlib** (заголовок `0x78 0xDA`), не gzip. В Go — `compress/zlib`.

Формат точки:
```json
{ "t": "2026-03-16T10:12:20+03:00", "pos": { "x": 37.617, "y": 55.755 } }
```
- `t` — время (ISO 8601); `pos.x` — долгота; `pos.y` — широта.
- Минимум 2 точки; приходить могут неотсортированными (сортируются внутри по `t`).

## Pipeline очистки

Маршрут проходит цепочку независимых стадий (`pipeline.Stage`):

```
Decode → sort_by_time          сортировка по времени
       → core                  ЧИСТКА: выбор самой тяжёлой физически связной цепочки точек
       → deduplicate           склеивает дубли (ближе DEDUP_DISTANCE_METERS И Δt < DEDUP_TIME_GAP)
       → collapse_stops        сворачивает стоянки (кучи точек в радиусе) в одну
       → simplify              Дугласа-Пекер (SIMPLIFY_MIN_METERS), не трогая осмысленные точки
       → reachability_guard    возвращает точки там, где упаковка сделала переход непроезжаемым
       → fill_gaps             ДОРИСОВКА: дыры связи прокладываются по дорогам
       → Encode → длина (TotalLength)
```

**Смысл порядка.** Сперва чистка: ядро выбирает настоящий маршрут и выбрасывает подделку. Потом упаковка — она уменьшает трек втрое, теряя 0.04 % километража. Потом страж: упаковка судит по геометрии и может создать переход, который не проехать. И только в конце дорисовка — по тому, что уже признано настоящим; рисовать дорогу через выброшенный спуфинг значило бы узаконить его.

### Чистка (`internal/core`)

Из трека выбирается самая тяжёлая **физически связная** последовательность точек. Вес точки — близость к дорожной сети (расстояние даёт OSRM), поверх него ложатся привилегии стоянкам и штрафы правил: ловушки, острова, два источника координат в одном треке, петли, лётные поля, приманки. Правила **не удаляют** точки, они только копят улики; удаляет один раз выбор цепочки, взвесив всё разом.

Переходы выбранной цепочки проверяются по дорогам, невозможные запрещаются, цепочка строится заново — до дюжины проходов.

Прежние четыре фильтра (якорь, телепорты, скорость, ускорение) в состав **не входят**: замер показал, что они режут асфальт — локальный фильтр решает по одному соседу, и одна плохая опора убивает всё за собой. Файлы и тесты оставлены в репозитории.

### Дорисовка (`fill_gaps`)

Между двумя честными точками трек идёт прямой, а машина ехала по дороге. Через такие дыры проходит 27 % километража, дорисовка возвращает +5.4 %. Точки, которых не было во входе, конвейер помечает, а времена на них раскладывает по доле пути; в ответ пометки пока не выведены — см. предупреждение в разделе про статус задачи.

Предохранители стоят на **крюке** (путь по дорогам / прямая), потому что завысить дорисовка может только им: крюк до ×1.3 принимается сразу, выше ×3 отклоняется всегда, между ними решает время (90 км/ч + допуск).

### Отказ и деградация

| случай | поведение | почему |
|---|---|---|
| OSRM ответил про < 90 % точек | **отказ** (`failed`) | вес точки без ответа — ноль, ядро оставляет только отвеченные, и километраж падает КРАТНО (50 % ответов = 50 % пробега). Ошибка незаметная, отдать такое хуже, чем не отдать ничего |
| кончился бюджет времени | результат + пометка `degraded` | ошибка ограничена: у ядра невыловленные переходы это ~2 % километража, у дорисовки недоспрошенные дыры остаются прямыми |
| `OSRM_URL` пустой | трек проходит насквозь, `degraded` + предупреждение | осознанная настройка, а не поломка, но километраж занижен и молчать об этом нельзя |
| воркер умер, Redis моргнул | задача возвращается в очередь уборщиком | результат не сохранён — работа не сделана; см. «Очередь: задача не пропадает» |
| задача обрывает обработку 5 раз подряд | `failed` с причиной | дело в самой задаче; гонять её по кругу — крутить сервис в перезапусках без объяснений |

Бюджет задачи (`RESOLVE_TIMEOUT`) делится: чистка получает 80 % оставшегося времени, хвост достаётся дорисовке.

Добавление стадии = новая структура в цепочке `pipeline.New`, без правок в остальном коде.

## Архитектура

```
cmd/
  server/        прод: HTTP + gRPC (async) + пул воркеров + подключение к Redis; graceful shutdown
  debugserver/   ТОЛЬКО для отладки: синхронная /v1/routes/resolve-collisions (без Redis/воркеров)
internal/
  config/        env → Config
  codec/         base64 ↔ zlib ↔ JSON ↔ []geo.Point (защита от zip bomb)
  geo/           Point, Haversine, длина, расстояние до отрезка
  taskstore/     Redis-слой: карточка задачи (task:{taskKey}) + очередь-поток (tasks:stream), TTL
  worker/        пул воркеров: очередь → чистка → результат в Redis → расписка → callback; плюс уборщик брошенных задач
  callback/      HTTP-клиент уведомления внешней системы (Laravel)
  service/       бизнес-логика Resolve: валидация → pipeline → длина; сборка клиента OSRM
  core/          ЧИСТКА: стоянки, веса, правила, выбор цепочки, проверка по дорогам
  osrm/          клиент маршрутизатора: снэпы, расстояния по дорогам, геометрия
  pipeline/      Stage + стадии очистки + общий блокнот прогона (RunState)
  api/           REST (async): router (chi), handler (submit/status/debug), middleware, errors, health
  grpcapi/       gRPC (async): handler, interceptors, server, health
  debugapi/      синхронный HandleResolve — только для debugserver (не для прода)
  gen/           сгенерированный код из proto (не редактировать)
  logger/        scoped-логгер в context (request_id в запросах, taskKey в обработке)
proto/           .proto
swagger/         сгенерированная Swagger-спека
```

**Порядок остановки:** сперва перестаём ПРИНИМАТЬ (HTTP и gRPC), и только потом дорабатываем взятое. Обратный порядок означал бы, что задача, поданная в окно выключения, получает `202` и номерок, а разбирать её уже некому. Вынесено в `gracefulStop` и закреплено тестом — внутри длинного `main` перестановку двух блоков не заметит никто.

**Язык сообщений:** тексты ошибок, предупреждений и имена событий в логе — по-английски. Комментарии в коде и сообщения тестов — по-русски: их читаем только мы.

Прод-`internal/api` — чисто асинхронный. Синхронная ручка вынесена в `internal/debugapi` + `cmd/debugserver`, чтобы прод её не содержал (на ней держится фронт-отладчик `ariadne-debug-proxy`).

### Middleware / Interceptors

- **REST:** Recover → RequestID (`X-Request-ID`) → Logger → LimitBody → ErrorMiddleware.
- **gRPC:** RecoverInterceptor → RequestIDInterceptor (`x-request-id` в metadata) → LoggerInterceptor.

| `CALLBACK_URL` | — | шаблон с `{taskKey}`; пусто = коллбэки выкл |
| `CALLBACK_RETRIES` | `3` | повторов сверх первой попытки |
| `CALLBACK_TIMEOUT` | `5s` | таймаут одного запроса коллбэка |

## Защита от перегрузки (3 уровня)

- **REST:** `MAX_BODY_BYTES` (middleware) → `MAX_DECOMPRESSED_BYTES` и `MAX_POINTS` (codec, оба ВО ВРЕМЯ разбора).
- **gRPC:** `GRPC_MAX_RECV_MSG_SIZE` → те же два потолка в codec.
- **Время:** `RESOLVE_TIMEOUT` на задачу, из него чистке 80 %; исчерпание не валит задачу, а помечает результат неполным (см. «Отказ и деградация»).

Три потолка, и каждый закрывает своё:

| потолок | от чего |
|---|---|
| `MAX_BODY_BYTES` | огромное тело запроса |
| `MAX_DECOMPRESSED_BYTES` | бомба сжатия: маленький архив, огромное содержимое |
| `MAX_POINTS` | дешёвые элементы: размер маленький, точек миллионы |

**Порядок здесь — не формальность.** Байтовый лимит не ограничивает ЧИСЛО элементов: самый дешёвый элемент массива это три символа `{},`, и двадцать мегабайт таких дают семь миллионов точек. Пока `MAX_POINTS` проверялся после разбора (в `service`), запрос на **27 КБ просил 1547 МБ** при `mem_limit: 256m` — один запрос убивал контейнер. Поэтому разбор потоковый: элементы читаются по одному, счёт проверяется на каждом, и расход ограничен `MAX_POINTS` независимо от того, что прислали.

## Сверка с эталоном

Алгоритм чистки перенесён с отлаженного прототипа на Python, и перенос **проверяется тестами на настоящих треках**, а не на слово. Золотые векторы лежат сжатыми в `internal/*/testdata`, снимаются скриптами прототипа (`goldcore.py`, `goldfill.py`, `goldpipe.py`).

| что сверяется | тест | треков |
|---|---|---|
| части ядра: стоянки, веса, правила, цепочка, проверка по дорогам, петли, амнистия | `TestGolden_*` в `internal/core` | 4–8 на правило |
| ядро целиком | `TestGolden_CoreMatchesPrototype` | 8 |
| дорисовка | `TestGoldenFill_MatchesPrototype` | 6 |
| **весь конвейер: вход → ответ** | `TestGoldenPipe_MatchesPrototype` | 7 |

Все запросы к OSRM записаны «плёнкой», поэтому тесты идут офлайн и одинаково. Промах по плёнке (Go спросил то, чего прототип не спрашивал) валит тест — это само по себе расхождение.

**Расхождение с эталоном — ошибка переноса, а не повод править эталон.**

Единственный случай, когда эталон меняют, — когда меняется НЕ поведение, а название. Так было 2026-08-12 с причинами отказа дорисовки: их переименовали с русских на английские. Порядок такой и только такой:

1. пересобрать вектор БЕЗ правок и убедиться, что он совпал со старым — то есть прогон воспроизводим;
2. поменять в прототипе, пересобрать всё, сверить со старыми с поправкой ровно на переименование;
3. расхождений быть не должно ни в одном поле, кроме переименованных;
4. и только теперь менять в Go.

Названия причин (`accepted`, `detour`, `physics`, `no route`) — это ДАННЫЕ, а не текст. Поменять их в одном Go нельзя: золотые тесты покажут поломку там, где её нет.
